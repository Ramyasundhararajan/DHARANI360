Fourteen agents, and how to wire each one in

An automation follows a rule. An agent makes a judgement — reads a scanned licence, decides a risk rating, writes the chasing email. This is every agent worth building into the portal, what each one is allowed to touch, and the steps to connect it to the code you already have.

Four rules that apply to all fourteen

01

The model never produces a number, a date or a recipient

Code computes the commission, reads the expiry, decides who owns the record. The model writes the sentences and makes judgements it can explain. This one rule is why the system stays auditable.

02

Every agent starts in propose-only mode

It suggests; a person confirms. An agent is promoted to writing on its own only after its proposals have been measured against real records — per document type, per form, not all at once.

03

Every run is on the record

One row in a new agent_runs table per run — input, output, tokens, cost, who accepted or rejected it — and every write stamped in the audit trail as agent:<name>, never as a person.

04

Decide deliberately what leaves the building

Passports, Emirates IDs and client contracts going to a model is a data-processing decision, not a technical one. Sign the DPA, turn off training on your data, and keep the highest-sensitivity documents on the shortest path.

Step 0 — the runtime every agent shares

Build this once. Each agent afterwards is a single file plus a hook, because the key handling, the cost cap, the tool layer and the logging already exist.

  1. Get an API key

    Sign in at console.anthropic.com → API Keys → Create Key. Copy it once; it is not shown again. Set a monthly spend limit on the same screen — it is the cheapest safety net you will ever configure.

  2. Add the dependency

    One line in requirements.txt, in the same optional style the file already uses for boto3.

    pip install anthropic
# requirements.txt
anthropic>=0.40

  3. Put the settings where every other setting lives

    Add to .env and to .env.example (no real value), then register them in config.py — add the key to SECRET_SETTINGS so it is masked, and to REPORTED so python config.py shows it.

    AI_ENABLED=1
ANTHROPIC_API_KEY=sk-ant-...
AI_MODEL=claude-sonnet-4-5
AI_MONTHLY_CAP_USD=50
AI_PROPOSE_ONLY=1

  4. Create the runtime module

    agents/runtime.py with one function every agent calls — ask(system, messages, tools=None). It reads the config, refuses when AI_ENABLED is off or the monthly cap is spent, retries once on a timeout, and returns the answer plus the token count.

  5. Create the tool layer

    agents/tools.py — thin, read-only wrappers over the functions db.py already exposes: get_records, count_where, expiring_items, global_search, related_records, get_attachments. Every wrapper takes the acting user's role and filters departments through access.py before returning a single row. An agent must never see more than the person it is acting for.

  6. Add the runs table

    A numbered step in migrations.py creating agent_runs: agent name, trigger, input reference, output, tokens, cost, status, decided_by, decided_at. Nothing is dropped, in keeping with how the rest of the schema behaves.

  7. Make the audit trail tell the truth

    Wrap every agent write in the audit context the code already has, so the History panel on a record says an agent did it.

    db.set_audit_context("agent:doc_reader")
db.update_record(form_code, record_id, values)
db.clear_audit_context()

  8. Add a review queue

    One page listing everything agents have proposed and nobody has decided on, with Accept / Edit / Reject. While AI_PROPOSE_ONLY=1 this page is the only way an agent's work reaches a register — and it is also how you measure whether an agent is good enough to promote.

  9. Prove it end to end before writing agent one

    A ping command that calls the model, writes an agent_runs row and prints the cost. Then add it to smoketest.py so a broken key is caught by the same 50 checks as everything else.

    python -m agents.runtime --ping

The agents

Numbered in the order they are worth building. Each assumes Step 0 is done; where an agent also needs an automation from the register, it says so.

01

Document Reader

Vision model

Turns a scan into fields. The single biggest reduction in typing anywhere in the portal — and it makes every expiry date trustworthy, because it came off the document rather than off a keyboard.

Reads
New attachments through storage.get() — Emirates ID, passport, visa, trade licence, title deed, Ejari
Writes
Proposed values for that form's fields, with a confidence per field
Judges
Which document type it is, and which field each value belongs to
GuardrailAn expiry date never reaches a register unconfirmed. Confidence below your threshold goes to the review queue, not the record.
Connect it
  1. Create agents/doc_reader.py with one entry point: read(attachment_id).
  2. Build the prompt from forms_data.FORMS — the form's own field list is the schema you ask the model to fill, so a new form is supported the day it is added.
  3. Hook /record/<form_code>/<id>/attach in app.py: after db.add_attachment(), queue the run. Never block the upload on it.
  4. Add a "Read from this document" strip to record_view.html with Confirm / Edit / Discard per field.
  5. On confirm, write through db.update_record() under the agent audit context.
  6. Measure on 20 real scans per document type before enabling that type. Emirates ID and trade licence first; handwritten anything last.
02

Compliance Watchdog

Text model + scheduler

Turns your daily digest from a list into a chase. It decides what to say to each person about each expiring document, and keeps saying it until the replacement is on file.

Reads
db.expiring_items(), the record owner, what was already sent, and the matching text in regulations_data.py
Writes
A per-person message, a renewal task with the right checklist, an escalation note
Judges
Tone, urgency and what the renewal actually requires
GuardrailRules choose the recipient and the deadline. The model only writes the words. A missed deadline must never be a model's fault.
Connect it
  1. Needs the in-app scheduler first (A-01 in the automation register).
  2. agents/watchdog.py — daily: pull expiring_items, group by owning person.
  3. For each group, ask the model for one message plus the renewal checklist for that document type, grounded in regulations_data.py.
  4. Send through the notification dispatcher (A-03), not directly through mailer.py.
  5. Write the resulting task into the todos register via the same path /todo/add uses.
  6. Keep email_digest.py running unchanged until the agent has been right for a month.
03

Register Analyst

Text model + tool use

Plain-language questions across all 112 registers — "which licences expire in Q4?", "which agents have leads nobody has touched?" — answered with links to the records the answer came from.

Reads
Read-only tools over db.get_records, count_where, expiring_items, global_search
Writes
Nothing. Answers only.
Judges
Which registers the question is about and how to phrase the answer
GuardrailEvery tool call carries the signed-in user's role and is filtered through access.py first. A receptionist asking about payroll gets the same 403 the URL would give them.
Connect it
  1. agents/analyst.py defining the read-only tools from Step 0's tool layer.
  2. Pass session's user and role into every tool call — scope before query, never filter the answer afterwards.
  3. Add an /ask route and put the entry point in the existing Search Everything box.
  4. Render every answer with the record links underneath, so any claim can be opened and checked.
  5. Log each question and answer to agent_runs; questions asked reveal what the dashboards are missing.
04

Staff Helpdesk

Retrieval + text model

Answers "how do I…" and "what does the regulation require for…" from your own material. You already ship 324 KB of regulation text in regulations_data.py that almost nobody reads — this is what makes it usable.

Reads
regulations_data.py, the Documentation page, README.md, OPERATIONS.md
Writes
An answer with a citation to the exact source paragraph
Judges
Which passage answers the question, and when nothing does
GuardrailNo citation, no answer. It quotes your library; it does not give legal, tax or immigration advice — the same limit section 14 of the README already states.
Connect it
  1. Index the sources into chunks with their headings kept as the citation label.
  2. Store the index in the existing database rather than adding a vector service — at this size, keyword plus embedding search in Postgres is enough.
  3. agents/helpdesk.py: retrieve first, answer only from what was retrieved.
  4. Add it to the sidebar next to Documentation, where people already go when stuck.
  5. Log unanswered questions — they are your documentation backlog, written by the people who needed it.
05

KYC & AML Risk Analyst

Screening API + text model

Rates a client Low, Medium or High with a written rationale, and lets the rating set its own re-screening interval instead of someone remembering to.

Reads
The KYC record, its attached ID and company documents, and the sanctions/PEP screening result
Writes
A proposed rating, the rationale, and an escalation record when High
Judges
Risk, and whether a screening hit is genuinely the same person
GuardrailThe agent may raise a rating on its own. It may never lower one — only a named compliance officer can, and that decision is logged.
Connect it
  1. Open a screening account (OpenSanctions, ComplyAdvantage or Dow Jones) and put the key in .env alongside the others.
  2. agents/aml.py runs the list check first — that part must stay deterministic and repeatable.
  3. Give the model the record, the documents and the screening result, and ask for a rating plus reasons.
  4. Hook the KYC form's submit path; write the result as a proposal on the record.
  5. Store the confirmed rating so the scheduler can drive re-screening — annual, six-monthly, quarterly.
  6. Keep every input and output for the retention period; this is the file a regulator asks for.
06

Inbox & WhatsApp Triage

WhatsApp Business API + IMAP

Reads the shared mailbox and the company WhatsApp, works out what each message is, and files it — the end of "forward it to me and I'll upload it".

Reads
Incoming mail and WhatsApp messages with their attachments
Writes
Attachments onto the matched record, new leads, tasks, or a review-queue item
Judges
New lead, document for record X, invoice, or noise — and how confident it is
GuardrailConfident matches file themselves; anything uncertain waits in the queue. Nothing is ever auto-deleted or auto-replied to on the company's behalf.
Connect it
  1. Register a WhatsApp Business number through 360dialog or Twilio; approve your message templates with Meta — this takes days, so start it early.
  2. Point an IMAP mailbox at the same handler for email.
  3. agents/triage.py classifies the message, then matches sender and references against db.global_search().
  4. File through db.add_attachment(), or open a lead, or park it for review.
  5. Show the confidence and the reason on every filed item so a wrong match is obvious and one click to undo.
07

Lead Responder

Text model + portal feeds

Answers a new enquiry in minutes rather than hours, in the language it arrived in, with three real listings from your own register attached.

Reads
The inbound lead, and matching stock from the properties register
Writes
A draft first reply, a suggested agent, a qualification score
Judges
Budget, intent, area and urgency from a two-line enquiry
GuardrailAuto-send only for an out-of-hours acknowledgement using an approved template. Everything substantive is the agent's own send, from their phone, one tap.
Connect it
  1. Needs lead capture and assignment first (D-01 and D-02).
  2. agents/lead.py: score the lead, then pick matching properties with db.get_records().
  3. Draft the reply in the language of the enquiry — Arabic, English, Russian, Hindi as your market requires.
  4. Push "Send / Edit / Discard" to the assigned agent through the dispatcher.
  5. Record whether the draft was sent as written — that number tells you when to trust it further.
08

Follow-up Writer

Text model

Writes the day-3, day-7 and day-30 message using what actually happened — the viewing, the feedback, the objection — instead of the same template everyone ignores.

Reads
The lead's history, viewing feedback, last contact, current stock
Writes
The next message in the sequence, ready to approve
Judges
Whether there is anything worth saying this week, and stays quiet when there isn't
GuardrailStops instantly on any inbound reply. An automated follow-up sent after a client has already answered is worse than none.
Connect it
  1. Needs the follow-up sequence engine (D-04).
  2. agents/followup.py drafts from the thread, not from a template.
  3. Batch them: one morning screen where an agent approves fourteen messages in a minute.
  4. Wire the auto-stop to inbound events from the triage agent.
  5. Cap frequency in code, not in the prompt.
09

Contract & Document Drafter

Text model + pdfout.py

Produces the tenancy contract, MOU, NOC or offer letter from the record, and tells you what is missing before it is sent rather than after it is signed.

Reads
The record and your approved template library
Writes
A numbered PDF attached to the record, plus a list of gaps
Judges
Free-text clauses, and whether anything required is absent
GuardrailLegal wording comes from your approved template. The model fills gaps and reviews; it does not invent clauses.
Connect it
  1. Load your real templates into a template register with named merge fields.
  2. Merge record → template in code. Deterministic, testable, no model involved.
  3. agents/drafter.py handles only the free-text sections and the completeness review.
  4. Render with the existing pdfout.py, number it with db.next_doc_no(), attach it to the record.
  5. Hand off to e-signature (C-03) so the signed copy files itself back.
10

Call & Meeting Notetaker

Transcription + text model

The portal already has calls, meetings and notes. This turns them into a summary, a next action and a date on the client's record — without anyone typing after the call.

Reads
Call recordings and meeting notes from /calls and /notes
Writes
A summary onto the linked client or lead record, and a todo for the next action
Judges
What was agreed, what was promised, and by when
GuardrailRecording needs consent and a notice at the start of the call. Keep the transcript with the record — a summary nobody can check is a rumour.
Connect it
  1. Store recordings through storage.py so they follow the same object-storage path as attachments.
  2. Transcribe with Deepgram or Whisper — pick one with solid Gulf Arabic and accented English.
  3. agents/notetaker.py: summary, decisions, next action, due date.
  4. Attach the note to the record found through db.related_records().
  5. Create the next action as a real todo, assigned and dated.
11

Listing Copywriter

Text model

Writes portal-ready listing copy in English and Arabic from the property record, in your house tone, within each portal's length and claim rules.

Reads
The property record, the media checklist, your tone guide
Writes
Title and description per portal, in both languages
Judges
What to lead with for that property and that buyer
GuardrailNever states a fact the record does not contain — no invented views, sizes, handover dates or amenities. Facts are merged in, not written.
Connect it
  1. agents/copywriter.py, triggered when a property reaches "Ready to list".
  2. Give it the permitted claim rules for each portal as part of the prompt.
  3. Marketing approves both languages on one screen.
  4. Approved copy travels with the portal feed (E-01), never pasted by hand.
12

Data Quality Auditor

Rules first, model second

Runs weekly across every register and hands back one list a person can actually clear: duplicates, impossible dates, missing mandatory fields, records that should be linked and aren't.

Reads
Every register, plus the orphan-column report from migrations.py status
Writes
A cleanup list with one-click fix and merge links
Judges
Only the ambiguous cases — "are these two Michael Chens the same person?"
GuardrailIt never merges anything. Merging records in a compliance system is a human decision, and the README is already honest that linking is name-matching, not keys.
Connect it
  1. Write the deterministic checks first — they are cheap and catch most of it.
  2. Send only the genuinely ambiguous pairs to the model, in batches.
  3. agents/quality.py on a weekly schedule, output to one page.
  4. Track the list's size week over week; it should fall, and if it climbs something upstream is broken.
13

Audit & Security Watch

Rules first, model second

Reads the audit trail the way an auditor would, and says something only when there is something to say.

Reads
db.list_audit(), db.list_login_log(), db.recent_login_failures()
Writes
A short note to the director — and nothing at all on a normal day
Judges
Whether a pattern is unusual for this company, and how to describe it plainly
GuardrailSilence is the expected output. An agent that produces a daily "all normal" email trains everyone to ignore it.
Connect it
  1. Baseline from thirty days of existing audit history — you already have the data.
  2. Deterministic thresholds decide what counts as unusual: lockout runs, bulk deletions, out-of-hours director access, sign-in from a new country.
  3. agents/watch.py asks the model only to describe the pattern in plain words.
  4. Send through the dispatcher to the director, with links into the Audit Trail page.
14

Management Report Writer

Text model

Writes the commentary on the monthly pack — what moved, what didn't, and what deserves a look — around numbers it is given and never allowed to compute.

Reads
The computed panel output from insights.py, as JSON, plus the previous period
Writes
The narrative section of the daily, weekly and monthly reports
Judges
What is worth pointing out, and what is noise
GuardrailThe model receives finished numbers and returns only sentences. If a figure in the commentary is wrong, the bug is in insights.py — which is exactly where you can fix it.
Connect it
  1. Needs scheduled reports first (K-02).
  2. agents/reporter.py takes the JSON insights.build() already produces.
  3. Ask for commentary against the prior period, with an explicit instruction to state no figure not in the input.
  4. Render into the report PDF above the charts; the director reviews before it goes wider.

The order I would build them in

  1. Step 0, then agent 01. The Document Reader pays for the runtime on its own, and every field it fills makes agents 02, 05 and 12 more accurate.
  2. 03 and 04 next — Register Analyst and Staff Helpdesk. Both are read-only, so they can go live while everything else is still propose-only, and they teach the office what an agent is safe to be asked.
  3. Then 02 and 05. Compliance is where the portal is strongest; these two make it act instead of report.
  4. 06 to 08 once WhatsApp is approved. The client-facing agents are the ones with a revenue number attached, and the ones a bad answer is most visible in — so they go after you trust the review queue.
  5. 09 to 14 last. Each is genuinely useful and none is load-bearing. Build them when the first eight have stopped surprising you.
